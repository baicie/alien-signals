# alien-signals 终端输出详解

## 概述

本文档逐行解析 alien-signals 响应式系统的调试输出，帮助理解其 push-pull 双向链表算法的工作原理。

## 示例代码

```js
import { signal, computed, effect } from "./esm/index.mjs";

const count = signal(1);
const double = computed(() => count() * 2);
effect(() => console.log(double())); // 打印 2
count(5); // 打印 10
```

三个核心概念：

| 概念 | 说明 |
|------|------|
| **signal** | 响应式变量，值可变 |
| **computed** | 计算属性，值由其他节点推导 |
| **effect** | 副作用函数，当依赖变化时自动执行 |

## 节点关系图

```
signal#1 (count)
    │
    │  deps / subs 双向链表
    ▼
computed#2 (double = count * 2)
    │
    │  deps / subs 双向链表
    ▼
effect#3 (打印 double)
```

## 完整输出逐行解析

### 第一阶段：节点创建

```
[signal.create           ] signal#1 initialValue = 1 flags = [Mutable]
[computed.create         ] computed#2 flags = [None]
[effect.create           ] effect#3 flags = [Watching|RecursedCheck]
```

**解析：**

| 日志 | 含义 |
|------|------|
| `signal.create signal#1` | 创建了一个 signal 节点，初始值为 1 |
| `flags = [Mutable]` | signal 有 Mutable 标志（值可直接修改） |
| `computed.create computed#2` | 创建了一个 computed 节点 |
| `flags = [None]` | computed 默认无标志（值由其他节点计算得出） |
| `effect.create effect#3` | 创建了一个 effect 节点 |
| `flags = [Watching\|RecursedCheck]` | Watching=正在观察依赖变化；RecursedCheck=检测循环依赖 |

### 第二阶段：effect 首次执行，收集依赖

```
[effect.create           ] effect#3 executing fn()...
[link              ] CREATE: dep #1 -> sub #2 ver = 0
[signal.link             ] signal#1 => computed#2
[signal.read             ] signal#1 => 1
[link              ] CREATE: dep #2 -> sub #3 ver = 0
2
[effect.create           ] effect#3 fn() done, deps collected
```

**解析：**

```
effect#3 开始执行
    │
    ├─► 读取 double()，触发 computed#2
    │       │
    │       ├─► computed#2 内部读取 signal#1（count）
    │       │       │
    │       │       ├─► link: dep #1 -> sub #2
    │       │       │   建立 signal#1 → computed#2 的依赖
    │       │       │
    │       │       └─► signal#1 返回当前值 1
    │       │
    │       ├─► double = 1 * 2 = 2
    │       │
    │       └─► link: dep #2 -> sub #3
    │           建立 computed#2 → effect#3 的依赖
    │
    └─► effect#3 执行完毕，打印 2
        deps collected = [signal#1, computed#2]
```

**依赖关系最终建立：**

```
signal#1 ──links──► computed#2 ──links──► effect#3
  deps: []       deps: [#1]        deps: [#2]
  subs: [#2]     subs: [#3]        subs: []
```

### 第三阶段：signal 写入变化

```
[signal.write            ] signal#1 pending: 1 => 5
[signal.changed          ] signal#1 flags = [Mutable|Dirty]
```

**解析：**

| 日志 | 含义 |
|------|------|
| `signal.write pending: 1 => 5` | signal#1 待处理值从 1 更新为 5 |
| `signal.changed flags = [Mutable\|Dirty]` | 值确实变化了，标记为 Dirty（脏） |

### 第四阶段：propagate（推送阶段）

```
[propagate         ] --- START --- from sub #2
[propagate         ] branch1: sub #2 set Pending flags = [M|P]
[propagate         ]   -> continue to sub #3 (single subscriber)
[propagate         ] branch1: sub #3 set Pending flags = [W|P]
[propagate         ]   -> notify sub #3 flags = [W|P]
[notify                  ] effect#3 queued at index 0 flags = [Watching|Pending]
[propagate         ] --- END ---
```

**解析：**

signal#1 的 subs 链表头是 `link(dep=#1, sub=#2)`，所以 propagate 从 `sub #2`（computed#2）开始。

```
propagate 从 computed#2 开始遍历：

  步骤 1: 处理 computed#2
    ├─► flags = [None]，无任何标志
    ├─► branch1: 设置 Pending -> [M|P]
    │         （注意：自动添加了 Mutable 标志）
    └─► single subscriber，继续处理 sub #3

  步骤 2: 处理 effect#3
    ├─► flags = [Watching]
    ├─► branch1: 设置 Pending -> [W|P]
    ├─► 有 Watching 标志，触发 notify
    └─► effect#3 进入队列，位置 0

  步骤 3: 遍历结束
```

**propagate 的五个分支（branch）决策表：**

| 分支 | 条件 | 动作 |
|------|------|------|
| branch1 | 无特殊标志 | 设置 Pending |
| branch2 | 有 RecursedCheck/Recursed/Dirty/Pending | 清除标志 |
| branch3 | 有 Recursed | R -> P |
| branch4 | 无 D/P 且链路有效 | 设置 R\|P + 检查 Mutable |
| branch5 | 其他 | 无操作 |

### 第五阶段：flush（执行阶段）

```
[flush                   ] ========== FLUSH START ==========
[flush                   ] running effect at index 0
```

进入 flush 阶段，开始执行队列中的 effect。

### 第六阶段：checkDirty（拉取阶段）

```
[checkDirty        ] START for sub #3
[checkDirty        ]   dep #2 flags = [M|P] sub #3 flags = [P]
[checkDirty        ]   -> branch3: dep is Mutable|Pending, no stack
[checkDirty        ]   dep #1 flags = [M|D] sub #2 flags = [M|P]
[checkDirty        ]   -> branch2: dep is Mutable|Dirty, calling update()
[signal.update           ] signal#1 current: (5 changed)
[checkDirty        ]   -> dep changed, dirty = true
[computed.update         ] computed#2 oldValue = 2
[link              ] UPDATE: dep #1 -> sub #2 ver = 1
[signal.link             ] signal#1 => computed#2
[signal.read             ] signal#1 => 5
[computed.update         ] computed#2 newValue = 10 CHANGED
[checkDirty        ]   -> sub #3 changed, dirty = true
[checkDirty        ] RETURN dirty = true
```

**解析：**

checkDirty 的核心职责：按需拉取，检查值是否真的变了。

```
checkDirty(sub = effect#3) 开始检查：

  步骤 1: 检查 dep #2 (computed#2)
    ├─► computed#2 flags = [M|P]
    ├─► branch3: 是 Mutable|Pending，且 link 上无其他订阅者
    │         不入栈，直接继续深入
    └─► 深入检查 computed#2 的依赖

  步骤 2: 检查 dep #1 (signal#1)
    ├─► signal#1 flags = [M|D]
    ├─► branch2: 是 Mutable|Dirty
    ├─► 调用 update() 同步值
    │       └─► signal#1: currentValue 从 1 变为 5，changed = true
    └─► dirty = true（值确实变了）

  步骤 3: 回溯，更新 computed#2
    ├─► computed#2 oldValue = 2
    ├─► 重新执行 getter（count * 2 = 5 * 2 = 10）
    ├─► computed#2 newValue = 10，CHANGED
    └─► sub #3 (effect#3) changed, dirty = true

  返回: dirty = true（需要执行 effect）
```

**关键点：Lazy 更新**

```
signal#1 在写入时就标记为 Dirty，但值实际上：
  - pendingValue = 5（新值）
  - currentValue = 1（旧值，还没同步）

直到 checkDirty 阶段，才真正同步：
  - updateSignal() 将 currentValue 从 1 更新为 5
  - 这就是 "Lazy"（惰性求值）策略
  - 不在写入时立即计算，而是延迟到读取时计算
```

### 第七阶段：effect 执行

```
[effect.run              ] effect#3 START
[link              ] UPDATE: dep #2 -> sub #3 ver = 2
[signal.link             ] signal#1 => computed#2
10
[effect.run              ] effect#3 DONE
```

**解析：**

```
effect#3 开始执行：

  1. 先清空 deps，重新收集依赖
  2. 执行 fn()，即 console.log(double())
  3. double() 被调用：
     ├─► 读取 computed#2 的值 10
     ├─► 更新 link: computed#2 -> effect#3，版本号从 0 变为 2
     └─► 返回 10
  4. 打印 10
```

**版本号变化回顾：**

| link 操作 | 版本号 | 含义 |
|-----------|--------|------|
| CREATE: dep #1 -> sub #2 | ver = 0 | 首次建立依赖 |
| CREATE: dep #2 -> sub #3 | ver = 0 | 首次建立依赖 |
| UPDATE: dep #1 -> sub #2 | ver = 1 | computed#2 重新收集依赖 |
| UPDATE: dep #2 -> sub #3 | ver = 2 | effect#3 重新收集依赖 |

版本号（`cycle`）在每次 `updateComputed` 和 `run` 开始时递增，用于检测依赖是否过时。

### 第八阶段：flush 结束

```
[flush                   ] ========== FLUSH END ==========
```

所有队列中的 effect 执行完毕，整个更新周期结束。

## 关键设计思想

### Push（推送）vs Pull（拉取）

| 阶段 | 机制 | 作用 |
|------|------|------|
| **propagate** | Push（推送） | signal 变化时，快速标记下游为 Pending |
| **checkDirty** | Pull（拉取） | effect 执行前，按需检查并更新脏值 |

### 为什么要分 Push 和 Pull？

```
假设有 100 个 effect 依赖同一个 signal

❌ 每次 signal 变化就立即更新所有 effect：
   count(1): 触发 100 个 effect 立即重新计算
   count(2): 触发 100 个 effect 立即重新计算
   count(3): 触发 100 个 effect 立即重新计算
   → 300 次计算，即使中间的值不会被读取

✅ Push + Pull 分离：
   count(1): 标记所有下游为 Pending
   count(2): 标记所有下游为 Pending（但可能覆盖之前的）
   count(3): 标记所有下游为 Pending
   flush:    只计算一次，合并所有中间变化
   → 1 次计算，性能最优
```

### 批量更新（batchDepth）

```
startBatch();
count(1);  // 只标记，不执行
count(2);  // 只标记，不执行
count(3);  // 只标记，不执行
endBatch(); // 统一 flush，只执行一次 effect
```

### 双向链表优化

alien-signals 使用双向链表而非递归：

```
❌ 递归方式（可能栈溢出）：
   function propagate(link) {
     notify(link.sub);
     for (sub of link.sub.subs) {
       propagate(sub); // 递归调用
     }
   }

✅ 链表 + 栈方式（无栈溢出风险）：
   用 nextSub/prevSub 在链表中移动
   用 stack 记录待处理的分支
   用循环 + labeled break 代替递归
```

## Flags（标志位）速查表

| 标志 | 值 | 含义 |
|------|-----|------|
| `None` | 0 | 无特殊状态 |
| `Mutable` | 1 | 值可直接修改（signal 有，computed 默认无） |
| `Watching` | 2 | 正在观察依赖变化（effect 有） |
| `RecursedCheck` | 4 | 检测循环依赖 |
| `Recursed` | 8 | 检测到循环依赖 |
| `Dirty` | 16 | 值已过期，需要重新计算 |
| `Pending` | 32 | 等待被处理（批量更新用） |
